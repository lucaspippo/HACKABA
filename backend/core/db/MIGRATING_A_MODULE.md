# Migrating a `core/*.py` module off JSON files, onto Postgres

This is the sequence Tasks 7-9 of
`docs/superpowers/plans/2026-08-24-polpilot-app-postgres-foundation.md`
followed to move `core/cuentas.py` off JSON. Repeat it once per remaining
module. Each module is its own small plan/PR — don't batch several together.
It found four real bugs the first time through; they're folded into the
steps below so the next module doesn't hit them again.

## 1. Read the module's current `_load`/`_save` (or equivalent)

Note the exact shape of the dicts/lists they return — every other function
in the file, and every caller in `angela.py`/`main.py`, already depends on
that shape. The migration must not change it (see `core/cuentas.py`'s
Spanish keys — `nombre`, `saldo`, `dias_sin_pagar` — preserved unchanged
even though the new table/column names underneath are English).

**Check whether the module has a *real* seed dataset on disk, separate from
its in-code fallback.** `core/cuentas.py`'s `_SEED` constant looks like "the"
seed data, but it's only the fallback for a tenant with nothing yet
(`piloto`, in tests) — the demo tenant's actual canonical numbers live in
the git-committed `data-demo/<file>.json`, generated by `data-demo/generar.py`.
Seeding every tenant from the in-code constant silently replaced demo's real
dataset and broke 19 "canonical number" tests before this was caught. This
applies even when the module has **no** `_SEED` fallback at all — `core/
audit.py`'s append-only log has none, but `data-demo/audit.json` is real
data (regenerated fresh by `generar.py` on every boot, gitignored rather
than committed, but still the tenant's actual seeded history) and needed
the exact same on-disk-first check, just with `[]` instead of `_SEED` as the
final fallback for a tenant with nothing on disk at all. If the module has
an equivalent on-disk file, the seed function must prefer it:

```python
def _seed_inicial() -> list[dict]:
    archivo = os.path.join(paths.DATA_DIR, "<archivo>.json")
    if not os.path.exists(archivo):
        return _SEED
    try:
        return json.load(open(archivo, encoding="utf-8"))
    except Exception:
        return _SEED
```

## 2. Design the table(s), with English table/column names

Every table gets a `tenant_id uuid not null references tenants(id) on
delete cascade` column and RLS policies (copy the pattern from migration
`0003_customer_accounts.py`: `ENABLE ROW LEVEL SECURITY`, `FORCE ROW LEVEL
SECURITY`, one `USING`/`WITH CHECK` policy on `tenant_id = current_setting
('app.tenant_id', true)::uuid`). If the module's JSON nests related records
(like `cuentas.json`'s `movimientos`), that's a second table with a
composite foreign key back to the parent, not a JSON column — keep data
queryable. Table/column names are English regardless of the Spanish domain
module they back; the *dict keys returned to the calling module* stay
whatever that module's existing callers already expect (step 1).

## 3. Write the Alembic migration

One file, `NNNN_<domain>.py`, `down_revision` pointing at the previous
migration's revision id. Add a `test_<domain>_tables_have_rls_enabled` case
to `tests/test_migrations.py` before writing it (write the test first, run
it, watch it fail, then write the migration).

## 4. Write `core/db/<domain>_repo.py`

English module and function names (`customer_accounts_repo.py`,
`list_accounts()`). Functions return the *exact* same dict/list shape the
old `_load()` did, including its existing (Spanish) keys. Include a
`seed_if_empty(tenant_id, seed)` function if the module has a `_SEED`
fallback today.

**Every query goes through `tenant_connection()` (→ `APP_DATABASE_URL`),
never `get_admin_engine()` (→ `DATABASE_URL`).** `DATABASE_URL`'s role is a
Postgres superuser locally (and typically the pooler/owner role in Supabase)
— superusers and any role with `BYPASSRLS` skip Row-Level Security
unconditionally, even on a table with `FORCE ROW LEVEL SECURITY`. Using the
admin engine for a tenant-scoped query doesn't error; it just makes RLS a
silent no-op. `get_admin_engine()` is reserved for genuinely non-tenant-
scoped work: looking up/creating rows in `tenants` itself
(`core/db/tenant.py`), and test fixtures that provision a throwaway tenant
(`db_tenant` in `conftest.py`).

**Never compare a Postgres timestamp against Python's local clock.** If the
domain has any expiry/TTL logic, do the comparison in SQL (`WHERE expires_at
> now()`), not `some_timestamp.timestamp() <= time.time()`. The app host and
its Postgres container can and do drift — an observed ~9s drift between a
dev machine and its local Docker/WSL2 Postgres broke exactly this kind of
check during the `sessions` migration.

**A `now()`-generated timestamp is UTC. Convert it before handing it back
to code that compares a date prefix against `core/fechas.py`'s `hoy()`.**
`hoy()` returns naive *local* `datetime.date.today()`. A row's `created_at`
(or any `server_default=now()` column) is a correct UTC instant — but
formatting it straight to ISO and slicing `[:10]` for a `<= hoy_iso` check
breaks near a UTC midnight boundary, which is routine for any timezone
behind UTC (Argentina's UTC-3 included — this broke `/api/actividad`'s
"today's corrections" filter within hours of writing the `audit_events`
migration, not in some rare edge case). Use `core.db.engine.to_local_iso(dt)`
on every timestamp read back from Postgres that used to come from
`datetime.datetime.now().isoformat()` — it converts to local wall-clock
time and drops the tzinfo, reproducing the old naive-string format exactly.
The mirror bug exists on the way *in* too: if a naive local-time string
(from a seed file, or computed in the calling `core/*.py` module before
being handed to the repo) is inserted into a `TIMESTAMP(timezone=True)`
column as-is, Postgres interprets it using the *session's* timezone (UTC
here), silently storing the wrong instant. Fix on write with
`datetime.datetime.fromisoformat(s).astimezone()` (calling `.astimezone()`
on a naive datetime attaches the correct local offset) before passing it as
the parameter — see `audit_repo.seed_if_empty()` and
`purchase_orders_repo.create()` for both directions of this fix.

## 5. Rewire the module's `_load`/`_save`

`_load` calls the repo's list function (seeding first if empty via
`_seed_inicial()` from step 1), `_save` calls the repo's upsert function(s).
Any function that mutates a *part* of the data (like `registrar_cobro`'s
single new movement) gets its own narrow repo call instead of a full
`_save()` of everything.

## 6. Run the module's existing test file(s)

They should need zero or minimal changes — they were testing behavior, not
storage. Two things reliably need updating:

- **Fixtures that reset state by deleting a JSON file.** `os.remove(cuentas.
  CUENTAS_JSON)`-style fixtures (`test_modulos.py`, `test_fable5_fixes.py`,
  `test_comprobantes.py` all had one) need a Postgres equivalent — see
  `conftest.limpiar_cuentas_db()` for the pattern (`DELETE FROM
  <movements_table>`/`<parent_table>` for the active tenant, so the next
  `_load()` re-seeds fresh).
- **Any test that mutates the module then asserts a canonical number in a
  *different* test file, across tenants sharing one process.** Run the
  *full* suite, not just the module's own test file, before calling this
  step done — file-order-dependent state leakage across the shared Postgres
  connection only shows up at full-suite scale, not in isolation. Run it
  **twice** to catch anything that only breaks on a second pass (a stale
  cache, a non-idempotent seed).
- **Add the new table to `conftest.py`'s `PILOTO_MUTABLE_TABLES` reset
  list.** The old JSON-file suite got a fresh "piloto" tenant for free —
  every `pytest` invocation started from a brand-new temp scratch directory
  (see the comment at the top of `conftest.py`). Postgres rows don't: they
  persist across *separate* suite runs, not just within one run. Skipping
  this step doesn't fail on the first `pytest` invocation after migrating a
  module — it fails on a *later, separate* one, once enough leftover rows
  from earlier runs accumulate to break a count/feed/limit-based assertion.
  Run the full suite **at least twice as two genuinely separate `pytest`
  invocations** (not just twice in a row within one process) to catch this
  — a single process, even run twice via `-q ... && -q ...` in the same
  shell command, won't reproduce it if nothing reset piloto's tables at
  that process's own conftest bootstrap.

**When a module's whole state is one blob (not per-entity rows)** — `core/
caja.py`'s single dict (`abierta`/`movimientos`/`historial`), `core/store.py`'s
full article list — a table with **one JSONB row per tenant** is the
faithful migration, not N normalized rows. These modules always read/write
the entire thing at once and compute everything in Python; nothing ever
queries a field in SQL. Forcing a many-row schema on data that's never
queried that way is extra design and mapping work for no real benefit — see
`inventory_working`/`caja_state` for the pattern (`tenant_id` primary key,
one `data`/`articulos` JSONB column, upsert-by-replace).

**`git checkout -- data-demo/` reverts tracked source files in that
directory too, not just the gitignored runtime JSON.** `data-demo/seed_db.py`
lives there — if you have uncommitted edits to it when you run the repo's
usual "restore the seeds" cleanup step after a test run, that command
silently discards them (git checkout only touches tracked files with
uncommitted changes; gitignored runtime files were never affected either
way, so the visible risk is entirely to files like `seed_db.py`). Commit
`seed_db.py` changes — or otherwise get them safely stashed — before
running that cleanup, not after.

## 7. Add the module's seed data to `data-demo/seed_db.py`

Prefer triggering the module's own `listar()`/equivalent (which already
knows to read the real on-disk seed vs. the fallback, per step 1) over
duplicating seed data inside `seed_db.py` — see how `seed_db.run()` calls
`core.cuentas.listar()` rather than reimplementing the seed-source choice.

**`seed_db.run()` must be tested via subprocess, not called in-process.**
`core.paths.TENANT`/`DATA_DIR` are resolved once at first import and don't
change if `POLPILOT_TENANT` is set later in an already-running process —
calling `seed_db.run("some-other-tenant")` from inside the test suite's own
process (which `conftest.py` already pinned to `piloto`) silently seeds the
*wrong* tenant. `seed_db.py`'s real callers (`deploy/boot.py`, a manual CLI
invocation) always run it as a fresh process, so match that in the test —
`subprocess.run([sys.executable, "-c", ...])`, same pattern several other
tenant-switching tests in this suite already use.

## Known follow-ups not covered by this playbook

- Full `users` table replacing the hardcoded `USUARIOS` dicts, plus an
  admin user-provisioning UI/endpoint (deferred — see Global Constraints
  in the foundation plan).
- Per-request dynamic tenant resolution for a single process serving
  multiple tenants (deferred — RLS ships now, routing topology doesn't
  change yet).
- Redis-backed sessions, if/when Postgres session-table latency actually
  becomes a bottleneck (not expected at pilot scale).
- A DB-backed replacement for the demo "reset" endpoint that the
  `POLPILOT_CANONICAL_DIR` file-copy mechanism provides for the still-JSON
  domains — `seed_db.py` covers the migrated domains (tenant, auth, cuentas)
  but there's no unified reset across both storage layers yet.
